# Архитектура Finance

Поток данных: Flutter screen → FinanceController → FinanceRepository → SQLite. Проверки и расчёты вынесены в FinanceEngine и валидацию repository; виджеты не служат источником финансовых данных.

```
lib/
  main.dart                      загрузка, темы, навигация, блокировка всех маршрутов
  domain/
    models.dart                  неизменяемые модели, JSON-контракты
    finance_engine.dart          деньги, балансы, периоды, бюджеты, повторения
    service_catalog.dart         расширяемый каталог подписок и RU/EN поиск
    bank_catalog.dart            СГЕНЕРИРОВАН: кредитные организации из справочника БИК Банка России
  data/
    finance_repository.dart      схема SQLite, atomic save/import, резервные копии
    demo_data.dart               демонстрационный семейный профиль
  services/
    security_service.dart        Android encrypted storage, PIN, биометрия
    notification_service.dart    разрешения, timezone, планирование уведомлений
  presentation/
    controller.dart              ChangeNotifier, последовательная очередь записей
    theme/app_theme.dart         цвета, шрифты, интервалы, темы компонентов
    widgets/                     карточки, операции, графики, цифровая панель
    screens/                     дашборд, операции, аналитика и management features
```

## Модель данных

Account, FinanceEntry, Category, Budget, Goal, RecurringRule, Member, AppPreferences — типизированные модели. Пользователь/семья представлены локальными Member, без серверной регистрации.

Таблицы SQLite: `currencies`, `members`, `accounts`, `categories`, `subcategories`, `entries`, `tags`, `entry_tags`, `attachments`, `budgets`, `goals`, `recurring`, `settings`. Включены foreign keys и индексы дат/категорий/счетов. Схема version3. Миграция v1→v2 добавляет `entries.toGoalId` и `recurring.paymentType`. Аддитивная v2→v3 добавляет архив категорий, идентификаторы/изображения сервисов и индивидуальные напоминания; старые счета, операции, семейные связи и явные настройки сохраняются. JSON и SQLite версии 1/2/3 поддерживаются. Удалённый параметр `hideAmounts` игнорируется; последние категории дохода/расхода хранятся независимо и очищаются, если связь недоступна.

Запись приложения проходит очередь контроллера и транзакцию базы. Импорт, восстановление и очистка демоданных используют ту же очередь, чтобы незавершённая запись не перезаписала восстановленные данные. Ошибка уведомлений после успешного commit не откатывает и не маскирует финансовую запись.

Repository сейчас атомарно записывает согласованное состояние целиком. Для очень больших историй нужны измерения и переход на инкрементальные записи, не меняя публичные финансовые инварианты. Не заявляется производительность на сотнях тысяч операций без профилирования.

## Инварианты

- Суммы — целое число минимальных денежных единиц с проверкой диапазона. Форматирование полных сумм и полей ввода также обходится без преобразования в double; double допустим только для геометрии диаграмм/процентов.
- Доход/расход связан с категорией соответствующего типа и существующим счётом той же валюты.
- Перевод имеет ровно одного получателя: другой счёт (`toAccountId`) или мечту (`toGoalId`). При разных валютах задаются две суммы. Категории дохода/расхода нет. Прогресс мечты — её начальное накопление плюс проведённые переводы; исходный счёт и резерв цели вычисляются из одной записи. Общий баланс включает только фактические переводы в резерв, а старый ручной прогресс повторно не добавляет.
- Pending/cancelled не входят в баланс, статистику и бюджеты. Периоды `[start,end)`.
- Финансовый месяц начинается в настраиваемый день1–28. Бюджеты относятся к текущему такому месяцу.
- Месячное/годовое повторение хранит `anchorDay`: 30янв→28фев→30мар, 31янв→28фев→31мар.
- Автоматическое создание идемпотентно: идентификатор операции содержит правило и дату наступления; одна запись не создаётся повторно при повторном открытии.
- Связанный счёт/участника нельзя удалить. Категория с операциями, бюджетом или регулярным правилом архивируется, сохраняя ID и историю; архив недоступен для новых операций. Историческую операцию можно редактировать с исходной архивной связью.
- Последняя категория обновляется в одной транзакции с новой ручной операцией. Редактирование существующего ID, отмена и ошибки сохранения её не меняют.

## Восстановление и будущая синхронизация

JSON имеет versioned envelope, проверку типов, ссылок, уникальности идентификаторов, денежных диапазонов и ограничений размеров. Внешние пути к вложениям не доверяются; встроенные данные чеков и пользовательских логотипов восстанавливаются в управляемый каталог приложения. Все проверки выполняются до замены финансового состояния.

У моделей стабильные UUID; repository является границей для будущего sync-adapter. Перед реализацией cloud sync понадобятся серверная авторизация, шифрование транспорта, tombstones, журнал изменений и стратегия конфликтов. Эти возможности не имитируются локальными переключателями.

## Визуальная система

Coffee: тёплый почти чёрный фон, кофейные поверхности, тауповые кнопки, лимонные выбранные состояния, молочный текст и коралловые расходы. Шесть прежних пресетов сохранены; дополнительно доступны пять палитр из `reference_palettes.dart` (Harbor, Forest, Lavender, Aurora, Royal/Nitro). Все пять используют один общий builder компонентов. Семантические цвета разделены через FinanceColors; пользовательские цвета категорий сохраняются. Графики рисуются локально CustomPainter без сетевых ресурсов. Поддерживаются system/light/dark; системный масштаб текста сохраняется.

Каталог содержит2 200 статических Material outline-иконок и18групп. Первые36числовых идентификаторов сохранены для совместимости; новые индексы фиксированы сгенерированным каталогом. Поиск нормализует русский/английский текст, е/ё, пробелы и синонимы. Picker использует ленивый SliverGrid.

Шестимесячный график строится по календарным месяцам независимо от финансового начала месяца, сохраняя выбранную валюту. Кольцевая диаграмма включает все категории; страницы меняют только видимые подписи вокруг кольца, а не расчёт. Проценты округляются до 0,1 методом наибольших остатков, чтобы сумма равнялась 100%.

Каталог сервисов содержит 246 стабильных ID в 13 группах и локальные SVG/PNG с индивидуальными SHA-256 и источниками. `ServiceSvgImage` растеризует неизменённый оригинал в 2× физическом разрешении, затем `Image` сглаживает уменьшение; стандартный ImageCache управляет кадрами. Временный keep-alive защищает незавершённый рендер при быстрой прокрутке/eviction; неудачный кадр очищается из pending cache. Официальные многоцветные изображения не получают одноцветный фильтр.

## Банки (1.6)

`bank_catalog.dart` генерируется `tool/bank_catalog.py` из официального справочника БИК (ED807, участники PtType=20): регистрационный номер, все БИК, официальное наименование, город. Брендовые названия и прежние имена для поиска заданы в скрипте по регномеру; сборка падает, если регномер исчез из реестра. `ServiceCatalog.entries` (246 сервисов) не меняется; банки доступны через `ServiceCatalog.banks`/`all`, группу `banks`, `byId` и поиск. `byName` для операций по-прежнему ищет только подписки. Логотип показывается только из записанного оригинального файла (`assets/banks/manifest.json`) через PNG-копию; иначе — нейтральный значок банка.
