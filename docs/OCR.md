# Offline receipt and bank screenshot OCR

Android uses **Tesseract4Android 4.9.0** (Tesseract 5.5.1), not the discontinued
`tess-two` artifact. Both Russian and English models ship in the application.
Recognition does not need internet, send a request to a server, download models,
or create a financial operation. Recognized fields still need user review.

## User flow

Use **+ → Чек или скриншот** (gallery or camera), the recognition button in a
new operation, a bank history screenshot/photo with multiple rows, or Android **Share → Finance** for a single image. PNG, JPEG and
WebP inputs up to 20 MiB are copied unchanged into private receipt storage.
The local parser proposes amount, merchant, date, type and an existing active
category (merchant history first, then Russian/English keyword rules). It does
not create categories or operations. Review all fields and explicitly save.
Bank history pages open a separate list of drafts with selection and row editing;
recognized captions can select any active category. Known merchant history takes
precedence. Possible already-saved duplicates start unchecked; equal legitimate
rows in the same new page are preserved. The whole selected batch is validated
against current data and saved in one repository transaction. Unknown fields must
be corrected or excluded, never silently coerced into RUB or an expense.

An ambiguous bank transfer requires a type choice; foreign-currency input
cannot silently become an operation in the selected account's currency. The
user can select/create a matching account or explicitly correct OCR currency.
Low recognition confidence and likely duplicates produce warnings. Cancelled,
unused draft copies are removed; saved receipt attachments are retained and
participate in the existing backup flow. Existing JSON export limits remain
10 MiB per image and 30 MiB total media; larger attachments need to be reduced
before portable export. No financial schema migration is required.

## Build inputs and licenses

Official wrapper: <https://github.com/adaptech-cz/Tesseract4Android/tree/4.9.0>.
The upstream README specifies the JitPack repository and dependency:

```kotlin
maven { url = uri("https://jitpack.io") }
implementation("cz.adaptech.tesseract4android:tesseract4android:4.9.0")
implementation("androidx.exifinterface:exifinterface:1.4.1")
```

The standard, single-threaded native variant is intentional: recognition jobs
are serialized on one background worker. The 4.9.0 upstream build enables
`ANDROID_SUPPORT_FLEXIBLE_PAGE_SIZES`; all four native libraries in its arm64
AAR have ELF LOAD alignment `0x4000` (16 KiB). This is a native library check,
not a claim that every Android device has been exercised.

Official `tesseract-ocr/tessdata_fast` models are pinned to commit
`87416418657359cb625c412a48b6e1d6d41c29bd` and use the LSTM-only engine:

## Contract

`ReceiptOcrService.recognize(privatePath)` invokes Android MethodChannel
`finora/ocr`, method `recognize`, with:

```json
{"path":"/data/user/0/com.finora.fintech/app_flutter/receipts/photo.jpg","language":"rus+eng","requestId":"receipt-1"}
```

`requestId` is generated by Dart (optional for direct native callers; the
default is `default`). Response: `{"text":"…","confidence":0.93,"lines":[…]}`.
`lines` is backward-compatible and optional: each line contains text, normalized
left/top/right/bottom coordinates and confidence, all numeric values in0..1.
Dart bounds and validates every coordinate before using it to join visual rows.
Confidence is Tesseract mean word confidence normalized to **0..1**. It is
neither a calibrated probability nor evidence that the amount is correct.
Empty text is a valid unsuccessful recognition result for the UI to explain.

The caller first copies gallery/camera/shared input into app-private storage.
The native implementation accepts only canonical paths below the application's
private data directory. It rejects external paths, symlink escapes, content
URIs and URLs. Shared content must be copied by the input flow before calling
OCR. The bridge does not retain a second image copy or log paths, text or amounts.

`cancel({requestId})` acknowledges cancellation and rejects the corresponding
recognition with `OCR_CANCELLED`. Dart also suppresses late results. Activity
destruction detaches the handler, cancels delivery and shuts down the executor.
The library's `stop()` API only documents HOCR recognition; this bridge uses
UTF8 recognition and never races `stop()` or `recycle()` against a running
native call. An already running native pass finishes before its resources are
released on the worker. Cancellation therefore cancels **delivery**, not a
guaranteed immediate halt of native CPU work. One additional job can wait;
further concurrent requests receive `OCR_BUSY`.

Stable errors include `OCR_INVALID_ARGUMENT`, `OCR_INVALID_PATH`,
`OCR_IMAGE_TOO_LARGE`, `OCR_INVALID_IMAGE`, `OCR_MODELS_MISSING`,
`OCR_MODELS_INVALID`, `OCR_OUTPUT_TOO_LARGE`, `OCR_UNAVAILABLE`, `OCR_BUSY`,
`OCR_CANCELLED` and `OCR_FAILED`. Dart adds `OCR_INVALID_RESPONSE` for malformed
bridge output and exposes localized messages without native exception details.

## Resource bounds and accuracy

Input is limited to **20 MiB** and **100 million source pixels**. Bounds are
decoded before allocating image pixels; decoding is bounded to12MP/8000px and prepared OCR pixels to8MP/6400px.
Ordinary1080px-wide tall screenshots retain their resolution. Temporary grayscale,
dark-background inversion and bounded upscaling improve small banking text. All eight EXIF rotation/mirror values are
handled. Only one native engine exists at a time. Bitmap and engine resources
are released in `finally`, including failed initialization or cancellation.
Recognized output is limited to 100,000 characters.

`PSM_AUTO` with one bounded `PSM_SPARSE_TEXT` retry, Russian plus English,
and a300DPI hint support ordinary receipts and screenshots. One pass is selected;
text from two passes is never concatenated. [Native1.5 changes and evidence](OCR_NATIVE_V15.md). Tiny text in long screenshots, blur, handwriting, stylized
bank layouts and photographs in poor light can reduce accuracy. Cropping or a
clearer image may be necessary. The domain parser separates bank history rows by geometry/date context and
protects itemized receipts from being imported as separate financial operations.
It cannot guarantee that every amount on an arbitrary photo has been read or
assigned correctly; compare the draft list with the image before saving.

```sh
flutter test test/receipt_share_service_test.dart
flutter analyze lib/services/receipt_ocr_service.dart test/receipt_ocr_service_test.dart
```

The OCR codec-level tests cover Russian/English text, path-only arguments,
unsupported/remote input, bounded result validation, native error mapping,
missing platform support, concurrent calls, cancellation and late-result
suppression, retries with unique IDs, and no network fallback. Upstream source
and the downloaded 4.9.0 AAR class signatures were inspected before writing the
bridge. These mocked channel tests do not exercise native OCR accuracy or
EXIF decoding; on-device checks must additionally include offline Russian and
English fixtures, rotated/mirrored photos, blank/malformed/oversized images,
activity destruction during recognition, cancellation and repeat use.

Fresh native verification: `:app:compileReleaseKotlin` passed with the permanent
Tesseract4Android/EXIF dependencies. Dart analysis of both services and both
test files found no issues; all **29** OCR/share codec tests passed in1.5. Native
recognition accuracy and Android intent/lifecycle behavior still require an
Android device or emulator; mocked channel tests do not establish them.

## Android image sharing

The `ACTION_SEND`, `image/*` share target accepts a single `content://` URI from
`EXTRA_STREAM` or single-item `ClipData`; it rejects `file://`, other schemes
and non-image MIME types. A background worker copies at most 20 MiB into a
UUID-named file under private `cacheDir/receipt_shares`. Content-provider size
metadata is checked when available; actual streamed bytes are always limited.
The URI is never sent to Dart or OCR and no upload occurs. A bounded queue and
`CancellationSignal` prevent unbounded copy jobs and cancel provider access on
activity destruction. Failed/partial and superseded unconsumed copies are
deleted. After consumption, the caller owns cleanup of the returned cache
file; copy it into the draft's private image directory if it must be retained.

`ReceiptShareService.imageAvailable` signals pending input; call
`takePendingImage()` after attaching the listener and whenever it emits.
`finora/receipt_share.takeSharedImage` consumes one pending path **or** one
pending input error, then returns null. Native `imageAvailable` and `shareError`
events both signal this consumption flow. Cold-start input/error stays pending
until taken, including when the native event precedes Dart initialization.
Native startup dispatch runs both after Activity creation and engine
configuration with per-Intent deduplication; warm intents use `onNewIntent`.

On desktop/test hosts without this optional native target, take returns null.
Actual Android input errors raise a localized `ReceiptShareException`.
Sharing never opens OCR or writes financial data inside the native bridge;
the authenticated Flutter UI chooses when to open and confirm the draft.

## Receipt total in 1.6

A shop/till receipt is always **one** draft. Its amount is the explicit
total only: `ИТОГ`, `ИТОГО`, `К ОПЛАТЕ`, `ВСЕГО`, `СУММА ПО ЧЕКУ`, `TOTAL`,
including a value on the next line or in a separate right column.

- Receipt evidence survives a partly lost header: fiscal fields (ФН/ФД/ФП,
  ККТ, кассир, смена, признак расчёта, nalog.ru), two or more `qty × price`
  rows, or a total together with item/tender lines. A total without signed
  bank rows also keeps the image out of the bulk-import path. Such text never
  becomes a list of operations; bank history pages with signed rows still do.
- Item prices, VAT, `ВНЕСЕНО`/`НАЛИЧНЫМИ`/`СДАЧА` and payment-method lines
  (`БЕЗНАЛИЧНЫМИ`, `ОПЛАТА КАРТОЙ`) are never the amount of a receipt and
  are never added up. Without an explicit total, or with two different totals,
  the amount stays empty with a warning for the person to enter.
- OCR-damaged labels are repaired only when damaged: `И Т О Г`, `ИT0Г`,
  `ИТOГО`, `К 0ПЛАТЕ`, `КОПЛАТЕ`; `≡` before a sum is read as `=`; a space
  before the decimal separator (`188 ,90`) is accepted.
- When native line coordinates exist, receipt text is parsed in visual rows,
  so `ИТОГ` meets the value printed far to the right even if Tesseract read
  the label column first. The text-only result is used only if the visual
  rows give no total; the draft keeps the original OCR text.

Regression evidence: `test/receipt_total_v16_test.dart`. Before the change,
three of its seven cases failed (right column, damaged label, missing total
silently taking a price); all pass now together with the previous parser,
statement, scan-import and editor tests. The fixtures are synthetic text and
coordinates, not photographs of real receipts.
